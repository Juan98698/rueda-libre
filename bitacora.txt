JUSTIFICACIÓN DE CONTROLES DEL FORMULARIO

1. Tipo de bicicleta (Radio buttons - input type="radio"):
   Se eligieron botones de radio porque son opciones mutuamente excluyentes (el cliente solo puede elegir un tipo de bicicleta principal). Al compartir el mismo atributo name="tipo_bicicleta", el navegador garantiza que solo se seleccione una opción a la vez.

2. Fecha del alquiler (input type="date"):
   Se eligió el campo de tipo fecha para que el navegador despliegue un selector de calendario nativo y estandarizado, evitando errores de tipeo y formatos ambiguos por parte del cliente.

3. Comentarios (textarea):
   A diferencia de un campo de texto simple de una sola línea, textarea permite al cliente ingresar texto multilínea con saltos de renglón para aclaraciones o solicitudes especiales.

COMPROBACIÓN DE HERENCIA EN DEVTOOLS (STYLES Y COMPUTED)

Objetivo de la prueba:
Verificar en el navegador cómo viajan los estilos desde el elemento padre (<body>) hacia los elementos 
hijos (<p>, encabezados) mediante el mecanismo natural de herencia en cascada de CSS.
Herramientas utilizadas:
- Google Chrome DevTools (Panel "Elements" -> subpaneles "Styles" y "Computed").
- Elemento inspeccionado: etiqueta de párrafo <p> en index.html.
--------------------------------------------------------------------------------------------------------
1. PROPIEDAD QUE SÍ SE HEREDA: 'color' (o 'font-family')
--------------------------------------------------------------------------------------------------------
- Declaración en el padre (body):
  color: var(--color-azul-noche);  /* #14213D */
  font-family: var(--fuente-texto); /* 'Open Sans', sans-serif */
- Evidencia en DevTools (Styles):
  Al inspeccionar el <p>, la propiedad no está escrita directamente en su regla, sino agrupada 
  bajo la sección "Inherited from body".
- Valor en DevTools (Computed):
  El navegador resuelve el valor computado final del texto del párrafo como rgb(20, 33, 61) 
  y la tipografía renderizada como "Open Sans".
- Justificación técnica:
  Las propiedades relacionadas con el texto (color, tipografía, interlineado) se heredan por diseño 
  en CSS. Esto asegura consistencia visual en todo el documento sin necesidad de repetir reglas 
  en cada párrafo o lista.
--------------------------------------------------------------------------------------------------------
2. PROPIEDAD QUE NO SE HEREDA: 'background-color' (o 'margin' / 'padding')
--------------------------------------------------------------------------------------------------------
- Declaración en el padre (body):
  background-color: var(--color-crema); /* #FAF6EF */
- Evidencia en DevTools (Styles):
  La propiedad 'background-color' NO aparece listada en la sección "Inherited from body" del párrafo <p>.
- Valor en DevTools (Computed):
  Al buscar 'background-color' en la pestaña Computed del <p>, su valor computado es:
  rgba(0, 0, 0, 0)  (es decir: 'transparent').
- Justificación técnica:
  Las propiedades del modelo de caja (margin, padding, border) y los fondos (background-color) 
  NO se heredan por defecto. Si un fondo se heredara, cada elemento hijo crearía una capa de color 
  opaca redundante sobre la anterior. El párrafo se ve color crema únicamente porque su fondo es 
  transparente y permite ver el fondo del elemento que está detrás (el <body>).



RESOLUCIÓN DE CONFLICTO DE ESPECIFICIDAD Y ESTADOS DE INTERACCIÓN


1. DESCRIPCIÓN DEL CONFLICTO ENCONTRADO
--------------------------------------------------------------------------------------------------------
Un compañero intentó aplicar un estilo para destacar la página activa mediante las reglas:
  #menu a { color: var(--color-gris); }
  .activo { color: var(--color-verde); font-weight: 600; }

Problema visual:
Al cargar el sitio, el enlace con la clase "activo" no se mostraba verde; continuaba viéndose gris.
En DevTools (panel Styles), la declaración 'color: var(--color-verde)' aparecía tachada con una línea.

2. CÁLCULO TÉCNICO DE ESPECIFICIDAD (ID, CLASE, ELEMENTO)
--------------------------------------------------------------------------------------------------------
El algoritmo de cascada de CSS resuelve colisiones entre reglas mediante la tupla (a, b, c):
- Columna 'a' (IDs): 100 puntos de peso.
- Columna 'b' (Clases, atributos y pseudoclases): 10 puntos de peso.
- Columna 'c' (Elementos/etiquetas y pseudoelementos): 1 punto de peso.

Comparativa de los selectores en conflicto:
- Selector '#menu a':
  * IDs: 1 (#menu)
  * Clases: 0
  * Elementos: 1 (a)
  * Vector de especificidad: (1, 0, 1) -> Peso: 101 puntos.

- Selector '.activo':
  * IDs: 0
  * Clases: 1 (.activo)
  * Elementos: 0
  * Vector de especificidad: (0, 1, 0) -> Peso: 10 puntos.

Diagnóstico:
El selector '#menu a' gana por tener mayor especificidad ((1, 0, 1) > (0, 1, 0)) gracias a la 
presencia del ID '#menu'. Por esta razón, el navegador descarta el color definido en '.activo'.

3. SOLUCIÓN IMPLEMENTADA (SIN USAR !important)
--------------------------------------------------------------------------------------------------------
Se elevó la especificidad del selector activo vinculándolo al contexto del menú:
  #menu a.activo { color: var(--color-verde); font-weight: 600; }

- Nuevo vector de especificidad para el estado activo:
  * IDs: 1 (#menu)
  * Clases: 1 (.activo)
  * Elementos: 1 (a)
  * Vector: (1, 1, 1) -> Peso: 111 puntos.

Resultado:
(1, 1, 1) supera a (1, 0, 1), aplicando correctamente el color verde y la tipografía seminegrita
sin recurrir a malas prácticas como '!important' o estilos en línea.

4. ACCESIBILIDAD Y FOCO VISIBLE (WCAG 2.4.7)
--------------------------------------------------------------------------------------------------------
- Navegación (#menu a): se añadieron estados :hover (color azul noche y subrayado) y :focus con 
  outline de 2px en verde ruta y outline-offset de 3px para usuarios de teclado.
- Llamada a la acción (.boton-cta): fondo verde ruta (#1E7A4F) con texto blanco (#FFFFFF), 
  ratio de contraste 5.31:1 (Cumple WCAG AA). Foco resaltado con outline naranja (#F39A2B).
- Formulario de reservas: se garantizó foco visible en input, select y textarea con borde y outline 
  contrastante al navegar con Tab.



EXPERIMENTO DE MEDICIÓN DEL MODELO DE CAJA (BOX-SIZING) EN DEVTOOLS


Elemento analizado:
Etiqueta <article> (tarjeta de servicio) en index.html.
Propiedades aplicadas:
- width: 47%
- padding: var(--espacio-md) (1rem = 16px por lado)
- border: 1px solid var(--color-gris) (1px por lado)
--------------------------------------------------------------------------------------------------------
1. MEDICIÓN CON box-sizing: content-box (Comportamiento por defecto del navegador)
--------------------------------------------------------------------------------------------------------
Valores obtenidos en DevTools (pestaña Computed):
- Content (ancho del contenido): 451.2px (equivalente al 47% del contenedor de ~960px)
- Padding (izq + der): 16px + 16px = 32px
- Border (izq + der): 1px + 1px = 2px
- Ancho total ocupado en pantalla = 451.2px + 32px + 2px = 485.2px.
Impacto visual observado:
El padding y el borde se sumaron por fuera del ancho declarado. Debido a estos 34px adicionales, 
las tarjetas exceden el espacio de la fila y la segunda tarjeta se desborda y cae a la siguiente línea.
--------------------------------------------------------------------------------------------------------
2. MEDICIÓN CON box-sizing: border-box (Reseteo universal aplicado)
--------------------------------------------------------------------------------------------------------
Valores obtenidos en DevTools (pestaña Computed):
- Ancho total asignado a la caja: 451.2px (exactamente el 47% declarado)
- Padding (izq + der): 16px + 16px = 32px (absorbidos internamente)
- Border (izq + der): 1px + 1px = 2px (absorbidos internamente)
- Content resultante disponible para el texto/imagen: 451.2px - 32px - 2px = 417.2px.
Impacto visual observado:
La caja respeta estrictamente el ancho asignado del 47%. Ambas tarjetas conviven perfectamente 
en la misma fila sin desbordamiento ni saltos inesperados.



MINIRETO 12: POSICIONAMIENTO, REVISIÓN FINAL Y LANZAMIENTO v1.0


Objetivo:
Aplicar esquemas de posicionamiento CSS avanzado a componentes clave, consolidar la consistencia 
arquitectural y visual entre las tres páginas y publicar la versión oficial 1.0 de Rueda Libre.

--------------------------------------------------------------------------------------------------------
1. DECISIONES TÉCNICAS DE POSICIONAMIENTO (RELATIVE, ABSOLUTE Y FIXED)
--------------------------------------------------------------------------------------------------------

A. Etiqueta destacada "Nuevo" (Servicio de bicicletas eléctricas):
   - Selector padre: 'section article' con 'position: relative'.
     * Justificación: Establece el bloque contenedor de referencia (containing block) local para sus 
       hijos posicionados, evitando que los elementos absolutos busquen el elemento <html> y se escapen de la tarjeta.
   - Selector hijo: '.etiqueta-nuevo' con 'position: absolute', 'top: 1rem', 'right: 1rem'.
     * Justificación: Al asignarle 'position: absolute', el elemento se extrae del flujo normal del documento 
       (out of flow). Por ello, flota en la esquina superior de la tarjeta sin empujar ni desplazar la imagen 
       ni los párrafos hermanos, logrando una tarjeta compacta y alineada.
   - Accesibilidad y contraste de la etiqueta:
     * Fondo: Naranja Pedal (#F39A2B).
     * Texto: Azul Noche (#14213D).
     * Ratio resultante: 7.20:1 (supera el estándar más exigente WCAG AAA > 7:1). Se descartó texto blanco 
       porque daba un contraste deficiente de 2.22:1 (inadmisible para accesibilidad).

B. Botón flotante de atención "WhatsApp":
   - Selector: '.boton-whatsapp' con 'position: fixed', 'bottom: 1.5rem', 'right: 1.5rem', 'z-index: 1000'.
     * Justificación: A diferencia de 'absolute', 'position: fixed' ancla el enlace a la ventana gráfica 
       (viewport) del navegador. De este modo, permanece siempre visible en la esquina inferior derecha 
       mientras el usuario navega y hace scroll en cualquiera de las 3 páginas.
     * Enlace seguro: href="https://wa.me/573000000000", target="_blank" con rel="noopener noreferrer" 
       para proteger contra vulnerabilidades de tabnabbing y mejorar el rendimiento de la nueva pestaña.
     * Foco y accesibilidad: Fondo Verde Ruta (#1E7A4F) con texto Blanco (#FFFFFF) (Ratio 5.31:1, cumple AA). 
       Cuenta con estado :focus resaltado con borde/outline naranja contrastante al navegar con la tecla Tab.

C. Prevención de solapamiento en el pie de página (Zona de seguridad):
   - Problema potencial: Al hacer scroll hasta el final del documento, un botón con 'position: fixed' 
     puede superponerse a los enlaces del footer (Google Maps o correo electrónico), impidiendo su lectura o clic.
   - Solución técnica: Se añadió 'padding-bottom: 4.5rem;' al elemento <footer> en styles.css.
     * Resultado: Se crea un colchón de espacio despejado de reserva en el fondo del documento, 
       garantizando que todo el contenido termine antes del área de acción del botón flotante.

--------------------------------------------------------------------------------------------------------
2. CONSOLIDACIÓN DE ESTILOS Y ORGANIZACIÓN DE styles.css
--------------------------------------------------------------------------------------------------------
Se refactorizó la hoja de estilos externa agrupando selectores repetidos y estructurándola en 6 secciones 
comentadas de acuerdo con los estándares de la industria y las directrices de Nodo Digital:
1. Variables y Reseteo: Paleta institucional (:root) y modelo de caja universal (box-sizing: border-box).
2. Estilos Base y Tipografía: Herencia de cuerpo (body), jerarquía tipográfica (h1 a h6) y contenedor <main>.
3. Encabezado y Navegación: <header>, lista #menu, estados interactivos :hover y foco accesible :focus.
4. Componentes y Layout: Botón CTA (.boton-cta), tarjetas de servicios, insignia (.etiqueta-nuevo), 
   botón WhatsApp (.boton-whatsapp) y tablas estructuradas (caption, th, td, filas alternas).
5. Formulario de Reservas: Fieldsets, legends, labels verticales, campos al 100%, estados :focus accesibles y botones.
6. Pie de Página (Footer): Contraste institucional unificado y zona de seguridad inferior.

MINIRETO: ENCABEZADO Y PIE FLEXIBLES CON FLEXBOX

Objetivo:
Modernizar el layout unidimensional del encabezado, menú de navegación y pie de página utilizando 
CSS Flexbox para mejorar la distribución en pantallas anchas y la fluidez en pantallas pequeñas.
1. Decisiones técnicas implementadas:
- Menú de navegación (#menu):
  * Se sustituyó el modelo antiguo de 'display: inline-block' y 'margin-right' por 'display: flex' y 'gap: var(--espacio-md)'.
  * Justificación: 'gap' elimina los márgenes residuales asimétricos en el último elemento y los espacios fantasma del HTML. 
    Se agregó 'flex-wrap: wrap' para permitir que los enlaces bajen de renglón si la pantalla es reducida.
- Encabezado (header):
  * Se aplicó 'display: flex', 'justify-content: space-between' y 'align-items: center'.
  * Justificación: Distribuye el nombre de la marca en un extremo y el menú en el opuesto, nivelando ambos elementos 
    en su eje vertical medio (eje cruzado). Con 'flex-wrap: wrap', el menú baja ordenadamente bajo el título en pantallas móviles.
- Pie de página (footer):
  * Se estructuraron tres bloques independientes (marca, contacto y horario de atención).
  * Se aplicó 'display: flex', 'justify-content: space-between' y 'align-items: flex-start'.
  * Justificación: 'align-items: flex-start' garantiza que las cabeceras de los tres bloques inicien exactamente 
    en la misma línea superior, a pesar de que el bloque de horario tiene 4 renglones y el de contacto solo 2.
2. Resultados de la prueba de redimensionamiento de ventana (Responsividad):
- Comportamiento en pantalla ancha (> 768px):
  * Encabezado: Marca a la izquierda y menú a la derecha en una sola fila compacta.
  * Pie de página: Tres columnas equilibradas horizontalmente a todo lo ancho del pie.
- Comportamiento al estrechar la ventana (pantalla móvil < 600px):
  * Encabezado: Al agotarse el ancho, el menú pasa automáticamente debajo del nombre sin generar desbordamiento ni scroll horizontal.
  * Pie de página: Los bloques bajan progresivamente de línea gracias a 'flex-wrap: wrap' y 'gap', apilándose verticalmente con espaciado uniforme y manteniendo la legibilidad total del contenido.

MINIRETO: CUADRÍCULA DE FLOTA ADAPTABLE CON CSS GRID Y FLEXBOX
========================================================================================================

Objetivo:
Construir una cuadrícula de tarjetas de producto adaptable y dinámica utilizando CSS Grid en dos 
dimensiones (sin media queries) y alinear el contenido interno de cada tarjeta con Flexbox unidimensional.

1. Decisiones técnicas implementadas:
- Contenedor de la flota (.cuadricula-flota):
  * Regla: 'display: grid; grid-template-columns: repeat(auto-fit, minmax(280px, 1fr)); gap: 1.5rem;'
  * Justificación: 
    - 'repeat(auto-fit, ...)' calcula automáticamente cuántas columnas caben según el ancho disponible.
    - 'minmax(280px, 1fr)' establece un ancho mínimo de 280px para evitar tarjetas aplastadas, y permite 
      que se expandan proporcionalmente (1fr) para llenar el contenedor.
    - 'gap: 1.5rem' genera separación uniforme horizontal y vertical sin márgenes asimétricos exteriores.
    - No requiere media queries para adaptarse a distintos dispositivos.
- Tarjeta individual (.tarjeta-bici):
  * Regla: 'display: flex; flex-direction: column; width: 100%; margin: 0;'
  * Box model: Fondo blanco, borde de 1px gris, border-radius de 8px y padding en rem (escala institucional).
  * Imagen fluida: 'width: 100%; height: auto;' para respetar la relación de aspecto panorámica sin recortar las ruedas.
- Alineación del botón de acción (.tarjeta-bici .boton-cta):
  * Regla: 'margin-top: auto; text-align: center;'
  * Justificación: Como las tarjetas en una fila de Grid tienen la misma altura pero descripciones de diferente 
    longitud, 'margin-top: auto' en el eje vertical absorbe todo el espacio vacío superior y empuja el botón 
    hacia la base de la tarjeta, logrando una alineación horizontal uniforme en toda la fila.
- Comprobación del 7.° modelo (Tándem):
  * Se agregó el modelo Tándem al HTML y la cuadrícula se reorganizó automáticamente de forma fluida, 
    creando una nueva fila sin necesidad de modificar ni una sola línea de CSS.

MINIRETO: LAYOUT GENERAL DE ESCRITORIO CON GRID Y FLEXBOX (NODO DIGITAL)
========================================================================================================

Objetivo:
Construir el layout general de las páginas combinando CSS Grid (para estructuras bidimensionales rígidas 
definidas en unidades 'fr') y Flexbox (para componentes unidimensionales basados en el flujo de contenido), 
siguiendo fielmente el boceto de escritorio de Nodo Digital.

Criterio fundamental de diseño:
- CSS Grid (2D / Bidimensional): Se emplea cuando la prioridad es la estructura y las proporciones del contenedor 
  (columnas y filas explícitas con 'fr'), independientemente de la cantidad o tamaño del contenido interno.
- Flexbox (1D / Unidimensional): Se emplea cuando los elementos fluyen linealmente en una sola dirección 
  (fila o columna) y su tamaño depende principalmente del contenido o necesitan distribuirse a lo largo de un eje.


REGISTRO DE LAS 6 DECISIONES DE LAYOUT:

1. Portada de Inicio (Hero):
   - Sistema elegido: CSS Grid (2D).
   - Regla CSS:
     .portada {
         display: grid;
         grid-template-columns: 1fr 1fr;
         align-items: center;
         gap: 2rem;
     }
   - Justificación (2D vs 1D):
     Se utilizó CSS Grid porque se requería una división rígida en dos columnas exactamente iguales (50% y 50% 
     usando '1fr 1fr'), donde el bloque de texto y la imagen del amanecer se reparten el espacio disponible 
     sin depender de la longitud del texto. 'align-items: center' permite alinear verticalmente el bloque de 
     texto justo en el centro óptico de la fotografía contigua.

2. Galería de Rutas Guiadas (Nuestras Rutas):
   - Sistema elegido: CSS Grid (2D).
   - Regla CSS:
     .galeria-rutas {
         display: grid;
         grid-template-columns: repeat(3, 1fr);
         gap: 1.5rem;
     }
   - Justificación (2D vs 1D):
     El boceto de diseño exigía estrictamente tres tarjetas en una sola fila. Con CSS Grid y la función 
     'repeat(3, 1fr)', el navegador garantiza 3 columnas simétricas con unidades fraccionarias ('fr'). 
     Además, las tarjetas dentro de la cuadrícula adoptan de forma natural la misma altura en la fila, 
     brindando orden visual sin trucos de márgenes o alturas fijas.

3. Distribución de Reservas (Formulario e Información 2:1):
   - Sistema elegido: CSS Grid (2D).
   - Regla CSS:
     .contenedor-reservas {
         display: grid;
         grid-template-columns: 2fr 1fr;
         gap: 2rem;
         align-items: start;
     }
   - Justificación (2D vs 1D):
     Se utilizó CSS Grid porque el layout del boceto demandaba una relación asimétrica estricta de dos tercios 
     para el formulario y un tercio para la barra lateral de contacto y horario ('2fr 1fr'). Las unidades 'fr' 
     calculan matemáticamente esta proporción exacta sobre el ancho total disponible. Se complementó con 
     'align-items: start' para evitar que el aside de contacto se deforme o estire forzosamente para igualar 
     la gran altura del formulario.

4. Fila de Campos Cortos Relacionados en el Formulario (Documento y Celular):
   - Sistema elegido: Flexbox (1D).
   - Regla CSS:
     .fila-campos {
         display: flex;
         gap: 1rem;
     }
     .fila-campos p {
         flex: 1;
     }
   - Justificación (2D vs 1D):
     Se eligió Flexbox porque es una relación estrictamente lineal (1 dimensión: fila horizontal). Son únicamente 
     dos campos de entrada que deben convivir en el mismo renglón. Con 'flex: 1' cada campo se reparte el 50% 
     del ancho disponible dentro del fieldset y 'gap: 1rem' mantiene una separación limpia entre ellos, 
     resultando mucho más semántico, simple y ligero que inicializar una cuadrícula Grid interna.

5. Encabezado Principal (<header>):
   - Sistema elegido: Flexbox (1D).
   - Regla CSS:
     header {
         display: flex;
         justify-content: space-between;
         align-items: center;
     }
   - Justificación (2D vs 1D):
     Se eligió Flexbox porque los elementos de navegación habitan a lo largo de un solo eje horizontal (eje principal). 
     'justify-content: space-between' empuja naturalmente la marca/logo al extremo izquierdo y el bloque de 
     navegación al extremo derecho, adaptándose de forma elástica a la longitud de los títulos y menús.

6. Pie de Página (<footer>):
   - Sistema elegido: Flexbox (1D).
   - Regla CSS:
     footer {
         display: flex;
         justify-content: space-between;
         align-items: flex-start;
         gap: 1.5rem;
     }
   - Justificación (2D vs 1D):
     Se eligió Flexbox porque organiza tres bloques de contenido textual (marca/ubicación, enlaces directos y créditos) 
     en un flujo horizontal continuo. 'align-items: flex-start' asegura que los tres bloques inicien parejos en la 
     línea superior, respetando las diferentes alturas de sus líneas de texto sin forzar cajones rígidos.

2. TRES PROBLEMAS RESPONSIVE IDENTIFICADOS Y RESUELTOS:

- Problema 1: Desplazamiento horizontal molesto en las tablas de tarifas en celulares (360 px).
  * Causa: En versiones anteriores se configuró '@media (max-width: 650px)' con 'white-space: nowrap' y 
    'overflow-x: auto'. Aunque permitía deslizar la tabla, el cliente reportó que 7 de cada 10 usuarios 
    navegan en celular y la experiencia de desplazarse de lado resultaba incómoda e impedía ver precios rápidamente.
  * Solución Mobile-First: Se eliminó el 'white-space: nowrap' y la media query max-width. En el CSS base móvil 
    se ajustó el relleno de las celdas a 'padding: 0.4rem 0.25rem' y el tamaño de fuente a '0.8rem' ('0.75rem' en th). 
    Con esto, las tablas de 4 y 5 columnas caben perfectamente dentro de los 360 px sin desbordamiento ni scroll lateral. 
    Posteriormente, en '@media (min-width: 768px)' se restaura la fuente a 1rem y el padding holgado.

- Problema 2: Colisión y desalineación del encabezado y pie de página en pantallas pequeñas.
  * Causa: El encabezado ('header') y el pie ('footer') utilizaban 'justify-content: space-between' en el CSS base. 
    En 360 px, el nombre de la empresa chocaba horizontalmente con los enlaces del menú y los tres bloques del pie 
    se envolvían asimétricamente hacia la izquierda generando desbalance visual.
  * Solución Mobile-First: En el CSS base móvil se aplicó 'flex-direction: column', 'align-items: center' y 
    'text-align: center'. Esto coloca el título arriba y el menú debajo centrado en el celular, y los bloques 
    del pie ordenados en una columna limpia. En '@media (min-width: 768px)', se recupera la distribución horizontal 
    del MiniReto 1 con 'flex-direction: row' y 'justify-content: space-between'.

- Problema 3: Portada, rutas y campos de formulario aplastados en columnas microscópicas.
  * Causa: Los layouts de portada ('1fr 1fr'), galería de rutas ('repeat(3, 1fr)'), reservas ('2fr 1fr') y la 
    fila de campos ('flex: 1') estaban definidos de forma fija en el CSS base. En 360 px, las rutas quedaban en 
    tres columnas de menos de 100 px cada una, y los campos Documento y Celular quedaban en menos de 130 px, 
    haciendo que los controles fueran difíciles de tocar y leer.
  * Solución Mobile-First: En los estilos base móvil todo se reestructuró a 1 sola columna ('1fr') y '.fila-campos' 
    se colocó en 'flex-direction: column' con ancho del 100%. Las divisiones multicolumna se delegaron a las 
    media queries con min-width: a 768 px la portada pasa a 2 columnas, las rutas a 3 columnas y los campos a fila; 
    y a 1200 px se activa la relación 2:1 en el formulario de reservas.


3. CRITERIOS TÉCNICOS CUMPLIDOS:
- Enfoque Mobile-First riguroso: Base móvil sin media queries, progresiones ascendentes con '@media (min-width: ...)'.
- Imágenes 100% fluidas con 'max-width: 100%; height: auto; display: block;'.
- Cero scroll horizontal a 360 px verificado en DevTools.
- Transiciones de layout consistentes en los breakpoints de 768 px (tablet) y 1200 px (escritorio).

MINIRETO: PROTOTIPADO RÁPIDO CON TAILWIND CSS PLAY CDN (CAMPAÑA RUEDA NOCTURNA)
========================================================================================================

Objetivo:
Crear un prototipo rápido y funcional de la sección principal para la nueva campaña "Rueda Nocturna" 
utilizando exclusivamente el Play CDN de Tailwind CSS y utilidades atómicas, sin hojas de estilo externas, 
sin la etiqueta <style>, sin atributos style="" en línea y sin clases de Bootstrap.


1. COMPARATIVA DE ENFOQUES: CONSTRUCCIÓN DEL BOTÓN (BOOTSTRAP VS TAILWIND)

a) Enfoque con Bootstrap (Semana 2 - Basado en Componentes):
   - Código utilizado:
     <a href="#" class="btn btn-primary">Inscríbete</a>
   - Cómo funciona:
     Bootstrap provee componentes "empaquetados". La clase '.btn' define el display, box model, padding 
     base, alineación y cursor; mientras que '.btn-primary' inyecta el color azul corporativo predeterminado, 
     el borde y los estilos para los estados :hover y :active.
   - Ventaja y limitación:
     Es inmediato de implementar, pero produce una interfaz estandarizada ("look Bootstrap"). Si el equipo 
     de diseño solicita un padding personalizado, un interletraje específico o un verde esmeralda con sombra 
     brillante para la noche, se hace obligatorio redactar reglas CSS externas para sobreescribir la 
     especificidad del framework.

b) Enfoque con Tailwind CSS (Semana Actual - Utility-First):
   - Código utilizado:
     <a href="#" class="inline-block bg-emerald-500 hover:bg-emerald-400 text-slate-950 font-bold px-8 py-3.5 rounded-xl text-base tracking-wide uppercase transition duration-200 shadow-lg shadow-emerald-500/20">
         Inscríbete
     </a>
   - Cómo funciona:
     No existe una clase mágica llamada '.btn'. En su lugar, el botón se construye ensamblando piezas 
     atómicas de propósito único:
     * 'inline-block': Permite que el enlace <a> adquiera dimensiones, rellenos y márgenes propios de un botón.
     * 'bg-emerald-500 hover:bg-emerald-400': Define el color de fondo base y su cambio interactivo al pasar el cursor.
     * 'text-slate-950 font-bold': Aplica contraste tipográfico oscuro sobre el fondo verde brillante con peso 700.
     * 'px-8 py-3.5': Establece un relleno horizontal de 2rem y vertical de 0.875rem (proporción táctil ideal).
     * 'rounded-xl': Redondea las esquinas con un radio de 0.75rem.
     * 'uppercase tracking-wide': Transforma el texto a mayúsculas y abre el espacio entre letras para legibilidad.
     * 'transition duration-200': Suaviza la transición de color durante 200 milisegundos.
     * 'shadow-lg shadow-emerald-500/20': Añade una sombra difuminada con tinte verde neón que refuerza el concepto nocturno.


2. DIFERENCIA CLAVE ENTRE UN FRAMEWORK DE COMPONENTES Y UNO UTILITY-FIRST

- Framework de Componentes (Alto nivel / Opinado - Ej: Bootstrap):
  Ofrece abstracciones ya construidas (botones, tarjetas, barras de navegación, modales). El desarrollador 
  adopta las decisiones de diseño que el framework ya tomó por él. Es ideal para tableros administrativos 
  o proyectos rápidos donde la originalidad visual no es prioridad.

- Framework Utility-First (Bajo nivel / No opinado - Ej: Tailwind CSS):
  No impone ninguna decisión estética previa ni componentes cerrados. En lugar de cajas prediseñadas, 
  entrega un sistema de diseño primitivo (escalas de espaciado, paletas cromáticas, tipografías y Flexbox/Grid) 
  directamente en el HTML. Permite diseñar prototipos completamente a medida y con identidad de marca 
  única a la velocidad de la luz, sin escribir una sola línea de CSS personalizado ni lidiar con nombres de clases BEM.

   - Resultado: Encontrada exitosamente en la línea 301 de 'src/output.css'.

     }

b) Búsqueda de clase no utilizada: 'bg-pink-500'
   - Resultado: 0 coincidencias en 'src/output.css' (completamente ausente).

c) ¿Por qué ocurre esto? (Justificación técnica):
   Tailwind CLI incorpora un motor de compilación Just-In-Time (JIT) / Tree-shaking. En lugar de generar 
   una hoja de estilos monolítica con las decenas de miles de utilidades posibles (lo que pesaría más de 3 MB 
   como ocurre con el Play CDN o frameworks tradicionales), la CLI escanea el código fuente de los archivos HTML 
   ('index.html'), extrae exclusivamente los nombres de clase que realmente fueron escritos por el desarrollador 
   y emite código CSS única y exclusivamente para esas clases detectadas.
   
   Por esta razón, 'bg-emerald-500' existe porque se usa en el botón principal, mientras que 'bg-pink-500' 
   es purgada y nunca viaja al navegador del usuario, reduciendo el peso final del CSS a solo ~17 KB.

3. JUSTIFICACIÓN DE DECISIÓN DE LAYOUT: GRID VS FLEX EN "¿CÓMO FUNCIONA?":

Para la sección de 4 pasos ("Elige tu ruta", "Inscríbete", "Recoge tu equipo", "Rueda"), se evaluaron dos alternativas:

A) Alternativa Flexbox ('flex flex-wrap'):
   - Enfoque unidimensional donde los elementos crecen o encogen según su contenido.
   - Desventaja: Si un paso tiene más texto que otro, el ancho de cada tarjeta tiende a variar o, al quebrar línea,
     las tarjetas inferiores pueden quedar desalineadas con respecto a la fila superior sin un ancho rígido manual.

B) Decisión tomada: CSS Grid ('grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-4 gap-6'):
   - Justificación:
     1. División estricta y simétrica: Cada paso representa una etapa cronológica de igual importancia (25% exacto de ancho en escritorio).
        CSS Grid garantiza que las 4 columnas tengan exactamente el mismo ancho sin depender de la longitud del texto.
     2. Altura uniforme automática: Por defecto, los ítems de un Grid se estiran a la misma altura de la fila ('stretch'),
        logrando tarjetas visualmente idénticas y alineadas.
     3. Responsividad predecible: Se adapta con fluidez de 1 columna (móvil) a 2 columnas ('sm:grid-cols-2' en tablets)
        y a 4 columnas ('lg:grid-cols-4' en escritorio).
     4. Semántica óptima: Se estructuró dentro de un contenedor <ol> (ordered list) con elementos <li>,
        comunicando a las tecnologías de asistencia una secuencia ordenada del 1 al 4.

1. DIAGNÓSTICO INICIAL EN 360 PX (AUDITORÍA DE ELEMENTOS ROTOS / DEFICIENTES):
Al inspeccionar la versión previa en DevTools simulando un viewport móvil de 360 px de ancho, se detectaron los siguientes problemas:
- Encabezado rígido y apretado:
  * El contenedor poseía altura fija ('h-20' / 80 px) y dirección horizontal forzada ('flex justify-between').
  * En 360 px, los elementos convivían forzadamente en una sola fila muy estrecha, con riesgo de desborde y sin aire vertical para interactuar.
- Distribución de Rutas desfasada:
  * La sección de rutas utilizaba 'md:grid-cols-2', lo que obligaba a pantallas entre 640 px y 767 px a mantenerse en 1 sola columna, desaprovechando el breakpoint 'sm'.
- Tipografía desproporcionada (Escala visual rígida):
  * El H1 del Hero ('text-4xl md:text-5xl') y los H2 ('text-3xl md:text-4xl') consumían demasiado espacio vertical en 360 px, empujando métricas y botones por debajo del primer pantallazo ("above the fold").
- Rellenos (paddings) y separaciones excesivas:
  * Rellenos de tarjetas 'p-8 md:p-12' consumían 64 px de padding horizontal sobre un ancho total de 360 px (dejando solo 296 px útiles).
  * La separación 'space-y-24' (96 px) entre secciones creaba huecos visuales excesivos durante el desplazamiento en celulares.
- Acciones del Hero:
  * Los botones con 'flex-wrap' quedaban asimétricos y difíciles de accionar con el pulgar en un smartphone.


2. REESCRITURA DE CLASES EN CLAVE MOBILE-FIRST (POR QUÉ Y PARA QUÉ):
El enfoque Mobile-First de Tailwind CSS consiste en definir estilos base sin prefijo (orientados a pantallas desde 0 px) y aplicar prefijos progresivos ('sm:', 'md:', 'lg:') mediante min-width media queries a medida que crece el viewport.

- Encabezado (<header>):
  * Clases aplicadas: 'py-3.5 md:py-0 md:h-20 flex flex-col md:flex-row items-center md:justify-between gap-3 md:gap-0'
  * Por qué: En móvil (360 px), el espacio horizontal es escaso para mantener el logo y los botones en una sola fila sin forzar colisiones.
  * Para qué: 'flex-col' apila verticalmente el logo sobre el botón CTA ("Inscríbete") con separación limpia ('gap-3'). Al llegar a 'md' (768 px), 'md:flex-row' y 'md:h-20' restablecen la barra horizontal tradicional de escritorio con altura fija de 80 px.
  * Navegación: Los enlaces se ocultan en móvil con 'hidden' (sin prefijo) y reaparecen desde 'md' con 'md:flex items-center gap-6'. El botón "Inscríbete" permanece visible en todos los tamaños como llamada a la acción principal.

- Rutas (<section id="rutas">):
  * Clases aplicadas: 'grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-6'
  * Por qué: Una tarjeta de ruta con imagen, métricas y botón requiere al menos ~280-300 px de ancho para ser legible.
  * Para qué:
    - Móvil (< 640 px): 1 columna ('grid-cols-1') para scroll vertical continuo sin overflow horizontal.
    - Tablet / Intermedio (≥ 640 px): 2 columnas ('sm:grid-cols-2') aprovechando el espacio horizontal disponible.
    - Escritorio (≥ 1024 px): 3 columnas ('lg:grid-cols-3') alineando las 3 rutas oficiales en una sola fila comparativa.

- Pasos "¿Cómo funciona?" (<section id="como-funciona">):
  * Clases aplicadas: 'grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-4 gap-6'
  * Por qué: 4 pasos cronológicos no pueden coexistir en pantallas angostas sin comprimir el texto a un estado ilegible.
  * Para qué:
    - Móvil (< 640 px): 1 columna ('grid-cols-1') que refleja la lectura cronológica natural paso a paso.
    - Tablet (≥ 640 px): 2 columnas ('sm:grid-cols-2') en cuadrícula simétrica 2x2.
    - Escritorio (≥ 1024 px): 4 columnas ('lg:grid-cols-4') en fila horizontal completa de izquierda a derecha.

- Tipografía y Espaciados Escalonados:
  * Título H1: 'text-3xl sm:text-4xl lg:text-5xl' (proporción óptima sin corte abrupto de palabras).
  * Títulos H2: 'text-2xl sm:text-3xl lg:text-4xl'.
  * Rellenos de tarjetas: 'p-6 sm:p-8 lg:p-12' (más área de lectura en móvil; holgura en escritorio).
  * Espaciado vertical entre secciones: 'space-y-16 sm:space-y-20 lg:space-y-24 py-8 sm:py-12 lg:py-20'.
  * Acciones del Hero: 'flex flex-col sm:flex-row items-stretch sm:items-center' (botones de ancho táctil en celular, fila centrada en tablets y computadores).

OPTIMIZACIÓN SEMÁNTICA: REDUCCIÓN DE DIVS Y ACCESIBILIDAD HTML5
Fecha: 2026-11-13
================================================================================

1. ¿SON NECESARIOS LOS DIVS SEGÚN EL ESTÁNDAR W3C/WHATWG?
- El elemento <div> no posee semántica intrínseca; representa un contenedor genérico.
- La especificación de HTML5 indica que debe usarse como "último recurso", cuando no existe ningún elemento semántico (<header>, <nav>, <main>, <article>, <section>, <aside>, <footer>, <figure>, <ul>, <ol>, <fieldset>, <address>, <p>) que represente fielmente el contenido.
- Casos donde el <div> es totalmente legítimo y necesario:
  a) 'Styling Hooks' de maquetación: Wrappers centrados con ancho delimitado ('max-w-6xl mx-auto') dentro de componentes de ancho completo (como <header> o <footer> fijos). Asignar etiquetas semánticas a simples cajas de centrado genera "sectionitis" y ensucia el árbol de accesibilidad.
  b) Agrupamiento en listas de descripción (<dl>): Desde HTML 5.2, el <div> está oficialmente admitido y estandarizado para envolver pares de <dt> y <dd> para facilitar cuadrículas CSS (Grid/Flexbox).

2. REFUNDACIÓN SEMÁNTICA APLICADA EN LA LANDING:
- Navegación principal: Se sustituyó el <div> contenedor de anclas por un menú semántico <ul class="hidden md:flex ..."> con elementos <li>.
- Sección Rutas: La cuadrícula principal pasó de <div> a un catálogo en lista <ul class="grid ..."> donde cada tarjeta es un ítem <li> que envuelve un <article>. Las imágenes se encapsularon en <figure>.
- Hero de Campaña: El bloque central se transformó en un <article> autocontenido dentro de <section id="inicio">.
- Formulario de Registro:
  * El agrupador de campos cambió de <div> a <fieldset class="border-0 p-0 m-0 grid ..."> con un <legend class="sr-only"> accesible.
  * Cada campo se estructuró semánticamente mediante <p class="space-y-2"> y el botón de confirmación se integró en el <footer> del formulario.
- Pie de página (Footer):
  * Los bloques de información y dirección física se organizaron en elementos <section> y <address>.
  * El texto de derechos reservados se migró a un elemento semántico <p><small>...</small></p>.

5. COMPARATIVA EN CUATRO CRITERIOS: BOOTSTRAP VS TAILWIND CSS

A) Curva de aprendizaje:
- Bootstrap: Muy accesible durante las primeras horas porque solo exige memorizar nombres prefabricados ('.btn', '.card', '.navbar'). Sin embargo, se vuelve frustrante y compleja en etapas intermedias y avanzadas, ya que cuando se requiere un diseño que se salga de la cuadrícula estándar, el desarrollador debe luchar contra la alta especificidad y los estilos 'encadenados' del framework.
- Tailwind CSS: Curva inicial más demandante porque no ofrece atajos prefabricados; exige dominar los fundamentos reales de CSS (Flexbox, Grid, Box Model, Box Shadow). Sin embargo, una vez asimilado el vocabulario atómico, la velocidad de desarrollo es exponencialmente mayor: no hay que salir del archivo HTML, no se generan nombres de clases artificiales (BEM) y no hay riesgo de regresiones visuales en cascada.

B) Nivel de personalización y diseño de marca:
- Bootstrap: Rígido y opinado. Todo proyecto nace con la apariencia inconfundible de Bootstrap. Adaptarlo a los 6 colores corporativos de Rueda Libre requiere compilar Sass, redefinir mapas de variables y escribir decenas de reglas de sobreescritura. El soporte para modo oscuro depende de selectores globales rígidos de tema.
- Tailwind CSS: 100% no opinado y maleable. Mediante la directiva '@theme' se integraron Crema (#FAF6EF), Azul Noche (#14213D) y Amarillo Farol (#FFD166) en segundos. El modo oscuro ('dark:') se aplica granularmente a nivel de utilidad sin librerías externas ni hacks de especificidad.

C) Tamaño final y optimización (Tree-shaking):
- Bootstrap: Monolítico. El navegador descarga el catálogo completo de estilos (grillas, tablas, formularios, botones, carruseles, acordeones) aunque la página únicamente requiera tres botones y una tarjeta.
- Tailwind CSS: Basado en compilación bajo demanda (*just-in-time tree shaking*). Solo se genera en el CSS final aquello que esté escrito en el HTML. Esto garantiza que sin importar qué tan grande crezca el proyecto, el CSS tiende a estabilizarse en un tamaño mínimo (en este caso, 6.5 KB gzip).

D) Casos de uso ideales:
- Bootstrap: Herramienta perfecta para tableros de administración internos (backoffices, dashboards), plataformas SaaS B2B, prototipos funcionales de hackatón o proyectos sin requerimientos de diseño estricto donde la velocidad de entrega del backend prima sobre la originalidad estética.
- Tailwind CSS: La opción predilecta para sitios web públicos, landing pages de marketing y conversión, e-commerce, sitios con manual de marca e identidad visual única (como Rueda Libre) y productos donde la optimización de Core Web Vitals y la experiencia en celulares sean críticas.

6. RECOMENDACIÓN FINAL Y JUSTIFICADA PARA RUEDA LIBRE:
Se recomienda de manera definitiva migrar la próxima versión de todo el sitio web de Rueda Libre a **Tailwind CSS**.
- Justificación técnica y de negocio:
  1. Identidad de Marca: Rueda Libre vende una experiencia emocional y turística en Medellín (rodadas nocturnas, luces, paisajes). La identidad no puede parecer una plantilla corporativa genérica de Bootstrap; requiere la elegancia de Azul Noche, la energía de Amarillo Farol y la frescura de Verde Ruta.
  2. Rendimiento Móvil: Como la campaña se difunde en redes sociales, el 85%+ de las visitas provienen de teléfonos celulares. Pasar de 57.7 KB a 6.5 KB en el payload de red disminuye la tasa de rebote en conexiones móviles.
  3. Mantenibilidad: La adopción de '@layer components' con clases puntuales como '.btn-primary' demostró que es posible mantener un HTML limpio y legible sin renunciar a la flexibilidad atómica de Tailwind.
